# Semantic model coverage roadmap for v0.3

> Status: **PLAN ONLY**. No v0.3 model is implemented, admitted or included in `0.2.1`.
> Last updated: November 8, 2026.

This is the public roadmap for expanding the scanner's reviewed semantic model coverage. It is
derived from measured planning evidence, not from a future coverage forecast. The published
`sfscanner@0.2.1` package, archive, website data and contracts remain the qualified baseline.

The owner has scheduled a long pause after the newly authorized scanner/workflow/library/analytics
overhaul. The prior `0.2.1` release remains the qualified baseline; the UI overhaul is not yet
qualified. There is no automatic resume. Work resumes only from a new owner decision and a fresh
baseline check.

## Measured starting point

| Measure | Current result |
| --- | ---: |
| Formal cohort workflows | 9,669 |
| Executable instances | 144,043 |
| Reviewed executable instances | 112 |
| Missing executable instances | 143,931 |
| Reviewed instance ratio | 0.0777545594% |
| Fully modelled workflows | 0 / 9,669 |
| Workflows with at least one reviewed instance | 67 |

The only formal reviewed scope is `n8n-nodes-base.gmail` `2.2.0`, resource `message`, with
`addLabels`, `delete`, `get`, `getAll`, `markAsRead`, `markAsUnread`, `removeLabels`, `reply`
and `send`. The absent-resource message default counts only where the pinned source proves it.
`sendAndWait`, other Gmail versions, other resources and other operations remain unreviewed.

The top-20 missing official types contain `95,746` of the `143,931` missing executable
instances, or `66.522153%`. This is backlog concentration. It is not achieved coverage, and it
does not forecast that `66.522153%` will be closed.

## Formal coverage is not legacy catalogue matching

Two measurements use similar words and must not be substituted for each other:

| Measurement | Current value | Meaning |
| --- | --- | --- |
| Formal reviewed executable coverage | `112 / 144,043` | Exact reviewed resource/operation behavior |
| Formal fully modelled workflows | `0 / 9,669` | Every executable requirement in the workflow is reviewed |
| Legacy catalogue matching | 1,107 observed types; 236,378 instances; 29 modelled, 10 partly modelled, 1,068 unmodelled | Existing resolver records, not formal review |

The promoted legacy catalogue already resolves `19 / 20` top-20 formal types and `19 / 20`
top-20 exact cohorts to `MODELLED`. The leading formal cohorts Code `2.0.0`, Set `3.4.0` and
HttpRequest `4.2.0` are already legacy-modelled. Therefore the top-20 formal backlog does not
prove that current generic-fallback or `DEGRADED` labels will fall.

Direct reduction of the current `DEGRADED` result states is `UNKNOWN`. Measuring it requires a
future mapping gate from each degraded workflow to its exact requirement and legacy resolver
outcome, followed by post-admission remeasurement. No rescan or new research is implied here.

## What this roadmap does not promise

- It does not promise `50-70%`, `95%`, `100%` or any other coverage percentage.
- It does not claim that full model review proves safety, exploitability or correct runtime behavior.
- It does not treat an absent parameter as an upstream default without exact pinned source evidence.
- It does not admit community-package expansion, automatic golden re-pins or blanket warning
  suppression.
- It does not relabel legacy catalogue matching as formal reviewed coverage.
- It does not change `0.2.1` package bytes, public data, contracts or archives.

## Readiness ladder

Every proposed model must move through these states in order:

1. `OBSERVED_REQUIREMENT` — measured in the frozen corpus with exact type/version and direct
   resource/operation presence or absence.
2. `METADATA_CANDIDATE` — an untrusted static proposal from pinned package metadata.
3. `SOURCE_IDENTITY_PINNED` — package, version, tarball and source paths bound in a receipt.
4. `SOURCE_BYTES_VERIFIED` — exact retained bytes were present and rehashed.
5. `BEHAVIOR_REVIEWED` — parameters, ports, selectors, behavior and security claims reviewed
   against exact source and fixtures.
6. `FORMALLY_ADMITTED` — independent approval matches the unchanged candidate manifest and
   runtime authority pins.

Today, `23` prioritized types have an identity receipt but no verified local bytes.
`@n8n/n8n-nodes-langchain.openAi` and `@n8n/n8n-nodes-langchain.lmChatGoogleGemini` have no exact
type receipt. No prioritized type is `LOCAL_SOURCE_READY` or formally admitted.

Package release versions (`n8n-nodes-base@2.15.1`, LangChain `2.43.5`) are separate from node
`typeVersion` values such as Gmail `2.2.0`. Neither substitutes for the other.

## Foundations

### F1 — Freeze and measure

Build a deterministic offline projection over retained scan records and the exact requirement
census. It must:

- preserve workflow identities and exact type/version;
- distinguish unknown from absent resource/operation values;
- calculate marginal missing instances only for a supplied candidate set;
- calculate whole-workflow completion only when every executable requirement is covered;
- emit stable ordering and digests without mutating retained evidence;
- emit each requirement's legacy resolver outcome and a before/after `DEGRADED` comparison.

Planning simulation is not formal runtime coverage. A v0.3 release claim requires the accepted
measurement producer or a separately authorized fresh frozen-corpus measurement.

### F2 — Source intake and metadata extraction

Prefer exact local source pins. Network acquisition requires a missing exact package/version and
controller authorization. Record package/version, tarball identity, integrity, retention and
licence basis, exact paths/bytes/digests, extraction limits and any source commit.

Static metadata extraction may propose only:

- node type;
- version candidate;
- parameter name and a proven literal default;
- port candidate;
- literal resource/operation label.

It must not import, execute, `require`, evaluate upstream code, invoke getters, follow dynamic
imports or infer a runtime default from absence. It must not propose taint sources or sinks,
endpoints, sanitizers, authentication facts, credentials, side effects, security effects or
actual dataflow.

## Batch sequence

Ordering is by coherent behavior family, not by promised coverage. Every batch is independently
admissible and revertible.

### B0 — Admission substrate

Build source-receipt verification, local-byte status, candidate schema and rejection diagnostics,
the candidate/evidence/manifest/admission digest chain, resolver fixtures, and the F1 projection.
No node behavior is admitted by B0.

Exit gates: altered bytes, missing files, traversal, dynamic values, constant cycles, duplicate
paths and over-budget extraction fail closed. Candidate bytes reproduce across two processes.
No candidate approves itself. Legacy `NodeCoverage` remains unchanged.

### B1 — Deterministic flow and transforms

Candidates: Set, If, Merge, Wait, SplitInBatches, Switch, SplitOut, NoOp and Aggregate.

Evidence must cover pass-through, branching, merge multiplicity, loops, aggregation and
stop/error behavior; ports and item modes; exact source files per admitted version; and explicit
fallback for unsupported versions or modes. Renaming or constructing an item is not proof that
taint was removed.

### B2 — Corpus ingress and scheduling

Candidates: ScheduleTrigger, ManualTrigger and Webhook.

Evidence must cover trigger entry points and ports, literal webhook method/path/authentication,
schedule and manual activation, disabled behavior, and the rule that reaching an edge does not
make a webhook payload trusted.

### B3 — Messaging integrations

Candidates: Gmail, Telegram and Slack.

Preserve the exact Gmail `2.2.0` message scope. Extend only exact version/resource/operation sets.
Evidence must cover selector extraction, reviewed operation sets, declared credentials,
destinations and send/write effects where exact source proves them. `sendAndWait`, draft/thread/
label resources and non-message operations remain conservative until separately reviewed.

### B4 — Google Workspace

Candidates: Google Sheets and Google Drive.

Evidence must cover resource/operation routers; exact sheet/range/spreadsheet and drive/file/
folder parameters; read, write, share, delete and move effects only where exact source supports
them; helper and transport closure; and operation-specific scopes rather than one broad record.

### B5 — HTTP boundary

Candidate: HttpRequest.

This batch cannot inherit a clean result from metadata. Evidence must cover method, URL, headers,
query, body, authentication, redirects, retries, response handling, bounded expression behavior,
credential resolution and request/response taint boundaries.

### B6 — AI and LangChain

Candidates: Agent, LmChatOpenAi, OutputParserStructured, LangChain OpenAi and
LmChatGoogleGemini.

The two missing exact type receipts block ordinary admission until resolved. Evidence must cover
model/tool/prompt connections and ports, prompt/response dataflow, tool invocation boundaries,
output-parser failures, provider and credential identity, and explicit malformed-output
behavior. Model output is never assumed trusted or sanitized.

### B7 — Code and taint-sensitive execution

Candidate: Code.

This remains separate because it is the largest backlog item and least suitable for ordinary
metadata admission. Evidence must cover exact source identity for each admitted version and
unknown-version handling, package boundaries, modes and languages, parameter facts, ports and
error behavior. It must state the limits of static JavaScript analysis and never claim that
arbitrary user code is sanitized, safe or fully modelled. Code may be deferred without blocking
smaller batches.

## Admission transaction

Each coherent slice follows one transaction:

1. Freeze exact source files and the source receipt.
2. Generate metadata candidates and diagnostics deterministically.
3. Build behavior evidence from exact source, pinned tests and reviewed local fixtures.
4. Freeze candidate records, manifest, evidence digest and fixture digest.
5. Obtain independent review from a non-producer with recorded authority.
6. Create approval over the unchanged manifest and evidence.
7. Update runtime authority pins only after approval.
8. Run focused resolver, adapter and consumer checks plus compatibility gates.
9. Recompute marginal instance coverage and whole-workflow completion from the same requirement set.
10. Retain the receipt, measured delta, failures and rollback identity.

Automation may compile, hash, compare and report. It cannot approve its own candidates.

## Gates and compatibility

Every slice preserves:

- exact Gmail `2.2.0` message behavior;
- generic fallback and both degraded coverage diagnostics for unsupported requirements;
- the distinction between unknown and absent values;
- duplicate-selector indeterminacy and direct-selector precedence;
- legacy `NodeCoverage` semantics;
- JSON, SARIF, CLI and Action compatibility;
- redaction and parser limits;
- no public-data mutation during extraction or admission.

Required checks include source-receipt rejection, manifest/digest integrity, resolver positive and
negative cases, consumer fallback behavior, exact workflow fixtures with whole-workflow
assertions, adversarial security vectors, format compatibility, marginal coverage before/after,
and the legacy resolver/`DEGRADED` mapping. No test count is a coverage claim; zero selected
tests is a failure.

Keep these measurements separate:

- reviewed instances / executable instances;
- fully modelled workflows / cohort workflows;
- exact-cohort missing incidence;
- top-N missing incidence;
- workflow union touching selected cohorts.

Do not sum overlapping incidents and call it coverage, and do not infer workflow completion from
an instance share.

## Rollback and release boundary

Each batch is a separate reversible admission unit. Failed or unreviewed candidates remain
outside runtime authority. Never auto-update goldens, source receipts or authority digests to make
a batch green. Keep the `0.2.1` package, archive, website data and published bytes unchanged.

Start v0.3 implementation only after the owner freezes the website/release baseline and explicitly
authorizes the work. One source writer owns a shared checkout; no nested agents write the same
paths.

## Resume sequence

1. Confirm the owner has lifted the long pause and frozen the current website baseline.
2. Recheck the `0.2.1` package, archive and public-site identities.
3. Reproduce F1 measurements from retained evidence without changing public data.
4. Select one coherent batch and verify its exact source bytes.
5. Complete the admission transaction and focused gates.
6. Publish internal marginal coverage and the `DEGRADED`-delta result.
7. Retain failures and rollback identity before starting another batch.

Initial completion means B0 is reviewed, one coherent behavior batch is approved with exact
source bytes and reviewed fixtures, the Gmail scope remains compatible, measurements are
recomputed, no unsupported selector is silently admitted, and residual unknowns remain visible.
No percentage target is promised.
